SCENE 01 — THE TARGET

You only see your own record

A timekeeping app, "Pointeuse". It shows your hours and quietly resets overtime to zero. A note says only a manager may see the real team register. The app remembers who you are with one cookie — profil.

What the app sends you
Connecté : Vous (#8472) — profil employe
Heures sup. : 0h « politique d'entreprise »

The whole challenge hides in that one word: employe. Where does it live, and who gets to change it?

SCENE 02 — SOLVE IT BY HAND

The cookie is a trust token you can rewrite

The profil cookie is a long string ending in ==. That shape is Base64 — an encoding, not encryption. Decode it and the app's trust decision is sitting there in plain text. Run it:

live · python in your browser
Click 1 to decode the real cookie…
Broken Access Control. The server put a trust decision — your role — into data the browser fully controls, with no signature. A JWT would carry a cryptographic signature; this doesn't. So you rewrite employe → manager, re-encode, and the server believes you. It's #1 on the OWASP Top 10 for a reason.

You just did the entire exploit by hand. Everything after this is about not doing it by hand.

SCENE 03 — LEVEL 0 · THE SCRIPT

The oracle is the only thing allowed to say "it worked"

Automating it is ten lines. But notice the last line — the oracle: a dumb, deterministic regex. It, and only it, decides success. That rule will matter enormously once an LLM enters the picture, because the LLM must never be the judge of its own success.

# solve.py — the exploit is hardcoded here (Level 0)
forged = base64.b64encode(b'{"employe":"...","role":"manager"}').decode()
r = requests.get(TARGET, cookies={"profil": forged})

# the ORACLE — the only judge of success
m = re.search(r"CyberZerk\{.*?\}", r.text)
Three roles, kept apart: something discovers, something executes, something verifies. Here you are the discovery. Next we hand that part to code.
SCENE 04 — RECON · MAKE IT DYNAMIC

Let the code find the lever itself

Hardcoding one exploit is a demo, not a program. recon.py takes any cookie, detects how it's encoded, decodes it, and flags the fields that smell like identity or role. Run the real module:

live · recon.classify()
Click to decode and map the levers…
Deterministic recon finds shapes, not meaning. It can tell you "there's a Base64-JSON cookie with a role key currently set to employe", and it pre-builds every escalation. What it cannot know is which one wins. That gap is exactly where an LLM earns its place.
SCENE 05 — REFRAME · THE MAP

The same facts, seen as a surface

A linear stepper implies one path and hides the alternatives. Drawn as a map, the whole attack surface is visible at once: one cookie forking into two lever-classes, the role lever fanning into concrete attempts. (This is the BloodHound lens — graph the relationships, don't list the records.)

Nothing new was discovered. The view changed — and a good view is most of what "a pain to use" actually means.

SCENE 06 — THE REASONING MODULE SIMULATION

An LLM as a typed module, not a magic agent

Now fill the gap recon left: which lever to try first. The LLM does not run free — it's a module with a typed contract. It receives a scoped projection of state (deps) and may only return something that fits the output contract (Rank | Ask | Answer). Malformed output can't leak through.

class Rank(BaseModel):          # the CONTRACT
    pick: str
    rationale: str

brain = Agent("mistral:…", output_type=Rank, deps_type=Projection)
result = brain.run_sync("rank the candidates", deps=projection)
result.output.pick     # guaranteed a str — or we never got here
simulation · typed planner output
deps (projection) → map + patterns
← output (validated)
{ "ranked": ["role=manager","role=admin","role=root", …],
  "rationale": "Unsigned Base64 role token — manager is the strongest escalation." }

Marked simulation: a real Mistral key can't ship in a public page. Run it for real with brain.py / recon_agent_v4.py in this repo.

Capabilities, not a persona. Reasoning is one module among others — fuzzy on the inside, strict at the boundary. The type is the fence. (Less James Bond, more Ocean's Eleven.)
SCENE 07 — THE AGENT · RANKED BATCH

Semantic order, deterministic sweep

Put it together: the menu is deterministic (recon.py), the order is the LLM's job, and the oracle still decides each hit. Fire them in ranked order, stop at the first flag. This part is real again — watch the console:

live · ranked batch vs. the dummy site
The sweep stops the moment the oracle sees a flag.
LLM proposes, oracle disposes, deterministic code sweeps. The probabilistic layer is boxed in on both sides — it can rank, but it cannot declare victory and cannot fire blindly.
SCENE 08 — THE SHAPE OF IT

Three layers, each with a different trust property

Data / Automation recon.py — deterministic · decode, enumerate
Reasoning brain.py — probabilistic, typed · rank only
Validation oracle — deterministic · the only "it worked"

The probabilistic layer is fenced by deterministic layers on both sides. The LLM proposes; the oracle disposes; a human pulls the trigger. That's the whole design — and it scales far past one cookie.

The honest limit. The candidate wordlist in recon.py is still hardcoded. The intelligence only re-orders a fixed list — it doesn't yet invent values. Letting the planner generate its own candidates is Lesson 1's open edge.

Not an intelligent little person with software attached — probabilistic reasoning as one capability among others.
